# Homologação v1.0.0-rc.14

> **Data:** 11/11/2026 · **Ambiente:** homologação (`master`, Cloud Run `saude-monitor-backend-hom`, banco `saude_monitor_hom`)
> **Rc anterior:** [`v1.0.0-rc.13`](./v1.0.0-rc.13.md) (09/11/2026) · **Origem:** `develop` no merge do PR #250
> **Responsável pela validação:** Raquel Fernandes (PO)

Esta rc leva o refresh do Painel Admin em cookie `HttpOnly` (item 7 do guia de pendências, ADR-013,
SEG-05, M-073). O backend ganha as rotas de sessão do painel, `POST /api/v1/auth/painel/login`,
`/refresh` e `/logout`, com o refresh só no cookie `__Host-painel_refresh`, defesa CSRF e CORS com
credenciais só para a origem do painel. O contrato do app não muda: login, refresh e logout do app
continuam como antes. O código do app é o mesmo da rc.13.

**Ressalva do domínio.** Em homologação o painel não tem hospedagem, e a API está em `…run.app`.
Com `SameSite=Strict`, o navegador só guarda o cookie com painel e API no mesmo site, o que depende
do domínio próprio da API (item 3) e da publicação do painel. Por isso esta rc valida em
homologação só o lado do servidor das rotas do painel e a regressão do app. O fluxo completo no
navegador fica para depois do item 3. Ver
[`Necessidades-Refresh-Painel-Cookie-v1.0.md`](../../02-arquitetura-tecnica/Necessidades-Refresh-Painel-Cookie-v1.0.md).

O roteiro da rc.13 ainda não foi preenchido. A rc.14 contém tudo da rc.13, então a seção 3 remete
a ele. A candidata à `release/1.0.0` passa a ser esta rc.

## 1. Como esta rc é gerada

O fluxo é o de [MANUAL.md §3.3](../MANUAL.md#33-promoção-para-homologação), sem passo manual além do merge:

1. PR `develop` → `master`. O check `Origem do PR (master)` só aceita a `develop` como origem.
2. No merge, o `cd-homologacao.yml` calcula a versão a partir de `expo.version` (`1.0.0`) e da
   última rc (`rc.13`): sai **`v1.0.0-rc.14`**, versionCode **1000014**.
3. Gera o APK HML assinado, publica o backend HML e roda os 3 smoke tests.
4. Confere que a URL embutida no APK responde e cria a tag e a GitHub Release (pré-release)
   com o APK e o changelog desde a rc.13.

O APK instala **por cima** da rc.13: mesma chave de assinatura e versionCode maior.

**Ordem backend e app:** só o backend e o painel mudam; o painel não é publicado pelo pipeline. O
APK é gerado de novo porque o pipeline sempre publica os dois; o código do app é o mesmo da rc.13.

**Configuração:** nenhuma variável nova é obrigatória. Sem `APP_CORS_PAINEL_ORIGIN`, o backend HML
usa o padrão `http://localhost:4200` para a origem do painel.

**Se o pipeline falhar:** nenhuma tag é criada quando a falha é no APK ou no backend. A rc.13
continua sendo a última publicada, e o `alarme-cd.yml` abre a issue "CD vermelho" para a
`master`. Corrigir na `develop` e promover de novo; o número `rc.14` é reaproveitado.

**Rollback:** reinstalar o APK da rc.13 exige desinstalar (versionCode menor). O backend volta
para a revisão anterior do `saude-monitor-backend-hom` no Cloud Run. As rotas novas do painel
somem com o rollback sem afetar o app, que não as usa.

## 2. O que entrou desde a rc.13

### Backend

| Assunto | PR | Melhoria |
|---|---|---|
| Rotas `POST /api/v1/auth/painel/login`, `/refresh` e `/logout`: só ADMIN (outro papel recebe o mesmo 401 de senha errada), access no corpo e refresh só no cookie `__Host-painel_refresh` (`Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`), rotação e blacklist por `jti` como no app | #250 | M-073 |
| `PainelCsrfFilter`: nessas rotas, `Origin` exatamente igual à do painel e `X-Requested-With: painel`, senão 403 | #250 | M-073 |
| CORS com credenciais só em `/api/v1/auth/painel/**` e só para a origem do painel (`APP_CORS_PAINEL_ORIGIN`, validada no startup); o resto da API segue sem credenciais | #250 | M-073 |
| Modo somente leitura aceita as três rotas do painel, como já aceitava o login do app | #250 | M-073 |

### Painel Admin (`admin/`, sem hospedagem)

| Assunto | PR | Melhoria |
|---|---|---|
| Access token só em memória, só o usuário no `sessionStorage`; sessão recuperada pelo cookie ao recarregar; login, refresh e logout pelas rotas novas | #250 | M-073 |
| Falha na renovação encerra só a sessão da aba (as abas dividem o cookie) | #250 | M-073 |

### App (Android)

Sem mudança. O código é o mesmo da rc.13.

### Documentação

ADR-013 passa a "Implementado"; `Especificacao-API-v2.4.md` §3.1 e §5; SEG-05 como 🟡 Parcial no

## 3. Roteiro de homologação

Marcar cada item no aparelho com o APK `radar-saude-hom-1.0.0-rc.14.apk` da página Releases. Os
itens de 3.2 rodam num terminal com `curl`, contra
`https://saude-monitor-backend-hom-767615581088.southamerica-east1.run.app` (chamado de `$HML`
abaixo).

### 3.1 App sem regressão no login (novo)

- [ ] Instalar por cima da rc.13 sem desinstalar e conferir que o app abre normalmente.
- [ ] Sair e entrar de novo com e-mail e senha: o login funciona como antes.
- [ ] Deixar o app logado por mais de 15 minutos e usar (abrir o Histórico, por exemplo): a sessão
      renova sozinha, sem voltar ao login.
- [ ] Sair pelo Perfil e reabrir o app: pede login.

### 3.2 Rotas do painel no backend HML (novo)

- [ ] `curl -s -o /dev/null -w "%{http_code}" -X POST -H "Origin: http://localhost:4200" -H "X-Requested-With: painel" $HML/api/v1/auth/painel/refresh`
      responde **401** (sem cookie).
- [ ] O mesmo com `-H "Origin: https://outro-site.example"` responde **403**.
- [ ] O mesmo sem o cabeçalho `X-Requested-With` responde **403**.
- [ ] Preflight: `curl -s -D - -o /dev/null -X OPTIONS -H "Origin: http://localhost:4200" -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type,x-requested-with" $HML/api/v1/auth/painel/login`
      traz `access-control-allow-credentials: true` e `access-control-allow-origin: http://localhost:4200`.

O login completo do painel não entra neste roteiro: homologação não tem conta ADMIN (seed
desligado) nem painel publicado no mesmo site da API.

### 3.3 Roteiro da rc.13

- [ ] Seções 3.1 e 3.2 do [roteiro da rc.13](./v1.0.0-rc.13.md#3-roteiro-de-homologação) (uso
      normal sem 429 e roteiro da rc.12 inteiro), com o APK da rc.14.
